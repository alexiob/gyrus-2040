# RP2040 board bring-up and SPI measurements

15 October 2026. Native diagnostic **built, flashed, verified, and exercised on
physical hardware**. Machine-readable results: [2026-10-15-results.json](2026-10-15-results.json).

## Board and firmware

- Waveshare RP2040-Touch-LCD-1.28, RP2040 silicon **B2**.
- Unique flash/USB ID `E463985803302D34`; BOOTSEL USB `2e8a:0003`;
  diagnostic CDC USB `2e8a:000a`.
- **16 MiB flash detected** by picotool, despite the advertised 4 MiB.
  Firmware retains a 4 MiB link limit; this diagnostic does not need more.
- LCD reset **GPIO13**, SPI1 on GPIO10/11, DC8, CS9, backlight25.
- CST816S-compatible touch ID **0xB5**, firmware 2, I2C address **0x15**.
- QMI8658 ID **0x05**, I2C address **0x6B**. Identity was tested; this milestone
  does not configure or qualify IMU motion measurements.
- Runtime CPU **125 MHz**, peripheral clock **125 MHz**, USB **48 MHz**.
- Final diagnostic static sections: text 47,644 B; data 0 B; BSS 118,596 B.
  BSS includes one 115,200-byte RGB565 diagnostic frame. These figures are not
  worst-case total RAM: runtime stacks and reserved sections are additional.

Tools are project-local: native macOS arm64 Arm GNU **15.3.Rel2 / GCC 15.3.1**,
Pico SDK **2.3.1** at its locked commit, TinyUSB at its SDK-pinned commit,
picotool **2.3.1**, pyserial **3.5**, CMake and Ninja. Verified package hashes
are in [dependencies.lock.json](../../dependencies.lock.json). The old x86_64
compiler in `/usr/local/bin` was not changed.

## Measurements

Each result below is **16 full 240 x 240 RGB565 transfers** on the final
firmware, including window commands and completion through SPI wire idle.
The SCK values are configured divider rates reported by SDK; no instrument
captured the physical waveform. Time is measured by the RP2040 hardware timer.

| Configured SPI | Method | Mean frame transfer | Worst in final batch | Transfers/s from mean | Touch reads during batch |
| --- | --- | --- | --- | --- | --- |
| 15.625 MHz | polling 16-bit | 64.529 ms | 64.543 ms | 15.50 | 16 |
| 15.625 MHz | DMA 16-bit | 64.536 ms | 64.642 ms | 15.50 | 104 |
| 31.25 MHz | polling 16-bit | 32.270 ms | 32.289 ms | 30.99 | 15 |
| 31.25 MHz | DMA 16-bit | 32.269 ms | 32.276 ms | 30.99 | 52 |
| 62.5 MHz | polling 16-bit | 16.142 ms | 16.180 ms | 61.95 | 15 |
| 62.5 MHz | DMA 16-bit | **16.148 ms** | **16.268 ms** | **61.93** | **26** |

A separate **576-transfer stress run** completed without a driver error:
96 frames per mode/rate. Its maximum full-frame DMA duration at 62.5 MHz was
16.278 ms. These are short bring-up runs, not long-term environmental qualification.

At 62.5 MHz, the ideal pixel payload takes 14.7456 ms. The observed full
transfer adds approximately 1.4 ms. The result is consistent with PL022 mode-0
inter-word gaps and command overhead; the gap length has not been measured
with a logic analyzer. A 60 Hz interval leaves only about **0.52 ms** beyond
the measured mean, so the game still needs overlap and/or dirty regions.

DMA does not improve the raw wire limit here. It lets the main core service
I2C while the same pixel transfer is underway. At the slow rate, the DMA batch
served 104 touch reads versus 16 with polling. At the fast rate it served
26 versus 15. No CPU-utilization percentage is inferred from these counts.

## Important clock correction found on the device

Calling `set_sys_clock_khz(125000, true)` left `clk_peri` at **48 MHz**, so the
first firmware's request for 40 MHz SPI actually produced **24 MHz**. A
hardware-result assertion expecting 125 MHz peripheral clock failed.

The final firmware explicitly selects `CLK_SYS` for `clk_peri` after setting
the CPU clock. The same assertion then passed, with CPU/peripheral/USB clocks
125/125/48 MHz. This is why the driver logs both source clocks and the actual
SPI divider rate rather than assuming the requested value was achieved.

## Display and touch checks

The user confirmed all of the following on the actual panel:

- Clean RGB color bars, with no random pixels or blank screen.
- A red cursor following finger movement on the grid and stopping on release.
- Clean black/white checkerboard and correct touch at **62.5 MHz SPI**.

Automated observations:

- Coherent touch reads and release states were received over USB.
- The initial interactive sweep reached x=15..239, y=0..235. It reported
  1,523 pressed samples, 2,363 touch IRQs, zero I2C transport errors, and
  maximum touch-read service time of **250 microseconds**.
- That boot also reported **28 rejected decoded samples out of 6,774 reads**.
  With zero transport errors, those reports failed the finger-count or
  coordinate validity checks. Raw rejected bytes were not retained, so their
  precise cause is not established. Invalid reports clear the pressed state.
- A later fast-profile boot reached x=8..215, y=14..204, with 399 pressed
  samples, zero rejected samples and zero I2C transport errors at the recorded
  protocol-check snapshot.
- 1 x 1 window transactions at four corners and the center completed without
  driver errors. Inclusive address conversion is also host-tested. Corner
  pixels outside the circular aperture cannot be visually inspected.

The read duration above is I2C/software service time, **not touch-to-photon
latency**. The controller scan cadence, firmware scheduling, frame transfer,
panel scan and LCD response all contribute to visible latency.

## Fault and protocol checks

Host C tests run with ASan/UBSan. They cover window bounds, touch report
validation, RGB565 patterns, printable command framing and embedded NULs. A
fake peripheral backend executes the real display driver with stuck DMA/SPI
states: the wait/abort is bounded, SPI stops before CS rises, and an
unacknowledged abort latches a fault preventing another transfer. A recoverable
failure requires a subsequent full-frame redraw before partial updates.

Four Python tests cover capped serial line length, an overall deadline while
bytes arrive continuously, partial lines across timeouts, and multiple lines
in a chunk. The host harness never uses unbounded `readline()`.

On the real board, unknown and overlong commands were rejected and a following
`info` command succeeded. The final firmware also rejected `boot\0anything`
without rebooting, then answered `info`. No physical bus-hang fault was injected.

## Reproduce

From the implementation checkout:

```sh
python3 tools/setup.py
cmake --preset host
cmake --build --preset host
ctest --preset host
cmake --preset firmware
cmake --build --preset firmware
```

Enter BOOTSEL by holding BOOT while reconnecting USB, wait for `RPI-RP2`, then:

```sh
.deps/picotool/picotool/picotool load -v -x build-rp2040/gyrus_board_diag.uf2 --vid 0x2e8a --pid 0x0003
```

This command replaces the firmware beginning at flash offset zero. It was
explicitly authorized for this bring-up. If several boards are attached, select
one with picotool's `--ser` rather than an ambiguous USB vendor/product match.

After the device reappears as a serial port:

```sh
.deps/venv/bin/python tools/diagnose.py info touch windows
.deps/venv/bin/python tools/diagnose.py bench --output artifacts/hardware/repeat.jsonl
.deps/venv/bin/python tools/diagnose.py 'speed fast' 'pattern checker'
.deps/venv/bin/python tools/diagnose.py 'stream on' --listen 30
.deps/venv/bin/python tools/diagnose.py 'stream off'
```

Only one process should own the serial port. Explicitly pass `--port` if
several Raspberry Pi serial devices exist. The firmware's `boot` command can
return it to BOOTSEL; wait for USB re-enumeration before running picotool.

Patterns are `bars`, `checker`, and `grid`; speeds are `slow`, `medium`, `fast`
(actual 15.625, 31.25, 62.5 MHz). Touch tracking is always active: while a finger
is down, the firmware replaces the pattern with a grid and red touch marker.
The final board was left at the fast rate with bars displayed.

## Remaining limits and next milestone

No overclocking, mode-3/PIO experiment, panel GRAM readback, tearing measurement,
logic-analyzer/oscilloscope capture, supply/temperature qualification or battery
runtime test has been performed. No guarantee of tear-free scanout is made.

This is the approved architecture's **single-core RGB565 diagnostic baseline**.
The indexed renderer, dual-core conversion/strip pipeline, dirty-region planner,
Sokol simulator and game remain future implementation milestones. The measured
baseline now supports those choices with real board evidence.
